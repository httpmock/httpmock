`httpmock` can record the requests your application sends to a third-party service together with the responses
that service returns. The recording is a YAML file that a mock server can later
[play back](/record-and-playback/playback/), so your tests no longer depend on the real service.

Recording needs the `record` cargo feature, which also pulls in `proxy`. The feature table is in the
[API reference](https://docs.rs/httpmock/latest/httpmock/).

There are two ways to get the traffic through the mock server: forwarding and proxy.

## Forwarding Strategy

Forwarding is the simpler of the two. It requires that you can point your client at the mock server's address
instead of the real service, for example by making the base URL configurable.

Your client sends requests to the mock server. The mock server forwards every request that matches the filter
of a forwarding rule to the target base URL and returns the target's response. Filters use the same
[`When`](https://docs.rs/httpmock/latest/httpmock/struct.When.html) structure you know from creating mocks. The rule
is created with
[`MockServer::forward_to`](https://docs.rs/httpmock/latest/httpmock/struct.MockServer.html#method.forward_to):

```rust
// Initialize the mock server for testing
let server = MockServer::start();

// Configure the server to forward all requests to the GitHub API,
// instead of using mocked responses. The 'when' configuration allows
// setting conditions for when forwarding should occur, using the same
// structure familiar from creating mocks.
server.forward_to("https://github.com", |rule| {
    rule.filter(|when| {
        when.any_request(); // Ensure all requests are forwarded.
    });
});
```

<Aside type="note" title="Hint">
    If no forwarding rule matches a request, the mock server falls back to its normal behaviour and tries
    to serve a configured mock response.
</Aside>

Forwarding replaces the host name of the request with the target. A recording made through a forwarding rule
therefore does not contain the host as a matching criterion, which is what lets you play it back on a mock
server that listens on a different address.

## Proxy Strategy

The proxy strategy is useful when you cannot change the base URL your client uses. Most SDKs and HTTP clients
support a proxy server setting instead. With the reqwest crate, for example, it looks like this:

```rust
// Create a client using the reqwest crate with a configured proxy
let client = Client::builder()
    .proxy(reqwest::Proxy::all("my-proxy-server:8080").unwrap())
    .build()
    .unwrap();

// Send a GET request and unwrap the result
let response = client.get("https://github.com").send().unwrap();
```

Each request now goes to the proxy server, which forwards it to the real host, `github.com` in this case.
When `httpmock` is that proxy, it can intercept, record and forward both requests and responses. Proxy rules
are created with
[`MockServer::proxy`](https://docs.rs/httpmock/latest/httpmock/struct.MockServer.html#method.proxy) and take the
same kind of filter as forwarding rules.

Proxying HTTPS traffic means the mock server terminates TLS itself. Your client needs to trust the mock server's
CA certificate for that; the [HTTPS page](/server/https/) explains how.

<Aside type="note" title="Hint">
    If no proxy rule matches a request, the mock server falls back to its normal behaviour and tries
    to serve a configured mock response.
</Aside>

## Creating the Recording

Forwarding and proxy rules only decide where requests go. The recording itself is started with
[`MockServer::record`](https://docs.rs/httpmock/latest/httpmock/struct.MockServer.html#method.record). Its rule
builder takes a `filter` that selects what gets recorded, again using `When`, and two options:
`record_request_headers` lists the request headers to store (by default none are recorded), and
`record_response_delays(true)` stores how long the real service took so playback can reproduce the delay. See
[`RecordingRuleBuilder`](https://docs.rs/httpmock/latest/httpmock/struct.RecordingRuleBuilder.html) for the
details.

Once your test has sent its requests, write the recording to disk with
[`Recording::save_to`](https://docs.rs/httpmock/latest/httpmock/struct.Recording.html#method.save_to), which takes the
directory and a scenario name and returns the path of the file it wrote. The file is named
`<scenario>_<timestamp>.yaml`; saving the same scenario twice within one second does not overwrite the first
file, the second one gets a counter suffix.
[`Recording::save`](https://docs.rs/httpmock/latest/httpmock/struct.Recording.html#method.save) uses a default directory,
`target/httpmock/recordings`, which it resolves from the `CARGO_MANIFEST_DIR` that `httpmock` itself was compiled
with. When `httpmock` comes from crates.io that is the registry checkout, not your project, so prefer `save_to`
with a path of your own and keep the returned path when you do use `save`. Use
[`Recording::export`](https://docs.rs/httpmock/latest/httpmock/struct.Recording.html#method.export) to get the
YAML as bytes without writing a file.
